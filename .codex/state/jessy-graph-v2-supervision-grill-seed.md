# Jessy Graph V2 Supervision Upgrade

## Goal

Turn the deviation patterns observed in the jessy-skills-only session into
deterministic Jessy Graph runtime controls, and make routed jessy-skills an
explicit part of worker code quality rather than an incidental global catalog.

## Locked Baseline

- Keep the host-native root systemd service and authenticated MCP on
  `0.0.0.0:8003`.
- Keep project-local runtime data, host `/root/.codex`, five-worker scheduling,
  internal worktrees, serial integration, and no automatic source write-back.
- Use only `deepseek-v4-flash` and `deepseek-v4-pro` for workers.
- Keep semantic project planning and final approval in the main Codex session
  using `project-workflow-codex`.

## Open Decision Branches

1. Contract rollout: should V2 replace the V1 contract and reject new V1
   submissions, or maintain a V1 compatibility adapter? This is TBD.
2. Plan approval: should a valid read-only worker plan proceed automatically,
   or should some task classes wait for main-session approval?
3. Skill authority: should the main session select `required_skills`, should
   Jessy Graph infer them from repository profiles, or should both participate?
4. Skill delivery: should workers rely on global skill discovery, or should
   Jessy Graph resolve full selected skill bodies and persist immutable hashes?
5. Worker capabilities: V2 should disable built-in multi-agent delegation and
   deny shell recursion into Codex, Git commits, and policy mutation before
   execution.
6. Git authority: V2 should require the task worktree HEAD to remain at the
   immutable base and compute changed paths from a controlled temporary index.
7. Verification isolation: should acceptance run in the worker worktree or a
   clean verifier worktree whose harness and policy hashes are worker-inaccessible?
8. Review roles: should every task receive a read-only semantic review, or only
   complex and high-risk tasks?
9. Model routing: should review always use `deepseek-v4-pro` while planning and
   implementation continue to route by task complexity?
10. Evidence policy: which reported evidence remains advisory, and which facts
    must be generated by Git, command runners, skill snapshots, and verifier
    artifacts?
11. Service rollout: should the upgrade stop the service and adopt a strict V2
    schema without runtime migration, or preserve queued V1 runs?
12. Acceptance: V2 must reject planning writes, reviewer writes, nested agents,
    nested Codex processes, worker commits, harness mutation, skill omission,
    reported-versus-actual diff mismatch, and source-worktree mutation.

## Recommended Direction

Use a strict V2 contract and fail-closed execution envelope. The main session
selects worker-safe skills, Jessy Graph validates them against a repository
quality profile, snapshots the full skill bodies, disables delegation, runs a
read-only planning turn, resumes the exact session for implementation, derives
the patch from the immutable base, verifies it in a clean worktree, and uses a
read-only semantic reviewer before serial integration.
